# 小说工具优化路线图（GitHub 复核版）

更新时间：2026-08-20

## 一、结论

当前工具不需要推倒重写。它已经具备商业策划、故事圣经、逐章生成、确定性检查、模型审查、状态台账、时间记忆、滚动细纲、失败修复、提交回执、发布镜像和断点恢复等关键底座。

当前 `BookRunner`、永久无窗口适配器、CLI `status/run/doctor`、连续正式尾段事务及逐章安全预检缓存已落地；Python 3.14 GUI 导入和372项测试已通过，既有81个子测试基线保留。真正阻碍“经过实证地自动写完整本商业小说”的问题收敛为四个：

1. 批次生命周期已脱离 GUI，但单章生产主体仍在 `gui_app.py`，尚未成为独立、逐状态可测试的整书状态机。
2. `target_total_chapters=30` 既承担规划窗口又承担终点，无法在每 15 章交接、每 30 章扩展后持续写到真正完结。
3. 模型被硬编码为单一型号，写作、规划、事实抽取、机械检查和商业审查没有角色化路由。
4. 现有测试能证明流程和证据链正确，不能证明小说更好看、更商业，也不能稳定比较模型或提示词版本。

优先解决这四项，再考虑平台数据回流、多智能体和复杂图数据库。

## 当前实施状态（2026-08-20）

- 已完成：`book_runner.py`、`headless_app.py`、`novel_cli.py status`、显式 `--execute` 的有界 `run`、严格只读 JSON `doctor`、项目锁与异常安全暂停。
- 已验证：Python 3.14 GUI 导入；全量372项测试通过，既有81个子测试基线保留；两个完结项目正式进度分别为300章、120章；足球项目第1—36章连续正式，严格 Doctor PASS。
- 已实证：足球项目完成真实批量生产、逐章审查、状态/正史同步、商业审稿、正式尾段重写与完整回滚保护；第36章已通过严格正式提交链。
- 未完成：独立 `run_state.py`、单章状态机拆分、15章自动交接包、通用30章滚动扩窗、独立任务级模型路由、固定商业评测集。
- 封存边界：两本完结书的历史派生状态/章节状态账本告警不修复、不续写，不作为新链路验收对象。

## 二、GitHub 参考结论

### 1. NovelClaw

地址：https://github.com/iLearn-Lab/NovelClaw

可借鉴：

- 把长篇写作视为持续工作区，而不是一次超长提示词。
- 章节、世界、角色、滚动摘要和记忆条目均可检查、可编辑、可追溯。
- 记忆检索同时保留结构化固定上下文、近期章节摘要和按问题检索的动态上下文。
- 每章候选稿经过检查、评分、修订后才成为当前最佳候选。

不直接照搬：

- 当前工具已有更严格的正式提交、哈希回执和失败关闭机制，不应替换。
- 多智能体循环成本较高，应先通过评测证明收益，再决定是否启用。

### 2. LongWriter / AgentWrite

地址：https://github.com/THUDM/LongWriter

可借鉴：

- 明确拆成 `plan -> section write -> assemble -> evaluate`。
- 分段结果缓存，失败时只重跑当前段，不重跑整本。
- 长文本质量和长度分别评测，避免“写够字数”等同于“写得好”。

不直接照搬：

- 它解决的是超长输出能力，不负责数百章连载中的人物状态、伏笔和商业节奏。
- 本工具应保留逐章正式提交，不把整本塞进一次模型输出。

### 3. LangGraph

地址：https://github.com/langchain-ai/langgraph

可借鉴：

- 持久化状态机、节点级检查点、失败后从精确节点恢复。
- 人工闸门是流程状态，而不是 GUI 临时变量。
- 每一步有显式输入、输出、状态迁移和重试边界。

不急于引入依赖：

- 先按同样思想抽出轻量 `BookRunner`。现有文件回执已足够充当检查点底层。
- 只有当分支、并发和恢复逻辑继续膨胀时，再评估是否迁移到 LangGraph。

### 4. Mem0

地址：https://github.com/mem0ai/mem0

可借鉴：

- 语义、关键词、实体和时间四种信号融合检索。
- 记忆有版本、来源章节、有效时间和覆盖关系。
- 记忆系统必须有专门评测，不能只看“能否搜到”。

不直接照搬：

- 当前 `state_ledger.py` 与 `temporal_memory.py` 已覆盖大量小说特有状态。
- 应增量补检索排序和记忆评测，不引入通用 SaaS 记忆层替换本地事实源。

### 5. OpenAI Evals

地址：https://github.com/openai/evals

可借鉴：

- 固定样本集、固定评分规则、版本化结果。
- 确定性规则与模型裁判分开记录。
- 比较模型或提示词时使用同一批输入，防止凭单次观感选型。

### 6. 次要参考

- GraphRAG：https://github.com/microsoft/graphrag
- TaleMate：https://github.com/vegu-ai/talemate
- SillyTavern：https://github.com/SillyTavern/SillyTavern

GraphRAG 对当前规模偏重。TaleMate 和 SillyTavern 的交互、人物卡和世界信息组织方式可参考，但其 AGPL 代码不应复制进本工具。

## 三、P0：完成这些，工具才算经过完整本生产验收

### P0-1 完成无 GUI 整书状态机抽取（部分完成）

已落地：

- `book_runner.py`：GUI/无界面共用的批次生命周期入口。
- `headless_app.py`：不创建 Tk 窗口的生产兼容桥。
- `novel_cli.py`：`status`、严格只读 `doctor` 和显式授权 `run`。

仍待完成：

- `run_state.py`：状态定义、迁移和恢复。
- 将 `batch_worker()` 的单章主体从 GUI 拆出。
- GUI 最终只保留事件绑定并调用独立服务。

状态至少包括：

`PREPARE -> PLAN_WINDOW -> DRAFT -> VALIDATE -> REVIEW -> REPAIR -> COMMIT -> UPDATE_MEMORY -> GATE -> NEXT_CHAPTER -> COMPLETE`

每个状态必须满足：

- 输入和输出可序列化。
- 重复执行不产生重复章节。
- 异常后能够从最后正式回执恢复。
- 只有 `COMMIT` 能写入正式 `output/` 与 `publish/`。

首个可用命令目标：

```powershell
py -3.14 -X utf8 -B novel_cli.py run `
  --project "projects/足球_百次复盘我成了世界中场" `
  --expected-latest 0 `
  --to 3 `
  --mode trial `
  --execute
```

足球项目必须先在第3章黄金三章硬闸门停止；当前没有 `resume` 子命令，不应在路线图中假设它已存在。

### P0-2 分离“整书终点、规划窗口、会话批次”（未完成）

配置应拆为：

- `book_end_mode`: `story_contract` 或 `fixed_chapters`。
- `book_max_chapters`: 安全上限，不代表必须写到此处。
- `planning_window_size`: 默认 30。
- `conversation_batch_size`: 默认 15。
- `current_planned_end`: 当前已有细纲终点。
- `next_generation_stop`: 本次会话停止章。

执行规则：

1. 每次只生成到本次 `next_generation_stop`，默认 15 章。
2. 每 15 章输出一个会话交接包，供新会话无损接续。
3. 距离细纲终点 3 章时，规划下一个 30 章窗口。
4. 只有“完结合同”通过，才进入 `COMPLETE`；到 30 章绝不能被当作整书结束。
5. 达到 `book_max_chapters` 但未满足完结合同时必须暂停，不能强行收尾或无限续写。

足球项目目前已有 `planning_horizon_only=true`、`auto_resume_full_book=false`、第3/10/30章硬闸门和书级终局合同，但这些尚未抽成所有项目共用的运行时状态机字段。

会话交接包建议落盘：

`handoff/第001批_001-015.json` 与同名 `.md`，内容包括正式章节范围、哈希、最新状态、人物变化、时间线、伏笔、商业债务、下一章合同、模型与提示词版本。

### P0-3 增加任务级模型路由

不要再把具体模型名散落在 `gui_app.py`、运行时和测试中。新增统一 `model_router.py`，按能力角色配置：

- `creative_primary`：正文初稿、关键重写。
- `architect`：商业蓝图、阶段大纲、滚动细纲。
- `reviewer`：商业性、人物弧、节奏和全书审查。
- `extractor`：结构化状态、摘要、实体和时间线抽取。
- `repair`：定向修订。

默认可全部映射到当前已验证模型；只有经过固定评测后，才把机械任务切换到更快或更便宜的模型。路由回执必须记录实际模型、提示词版本、输入输出 token、重试次数和失败原因。

### P0-4 建立“商业小说评测集”

新增目录：

```text
evals/
  cases/
  rubrics/
  baselines/
  results/
```

第一版固定 30 个案例：

- 黄金三章 6 例。
- 单章爽点兑现 5 例。
- 章节钩子 4 例。
- 人设与动机一致性 4 例。
- 时间线、比赛规则和能力边界 4 例。
- 连续 10 章节奏漂移 3 例。
- 套话、AI 腔、重复模板 2 例。
- 完结回收与情绪兑现 2 例。

每次修改模型、提示词、记忆或审查流程，都必须输出同一批案例的对比结果。没有基线提升，就不把改动用于正式整书。

## 四、P1：完成 P0 后再做

### P1-1 改进记忆检索，不替换记忆底座

- 为每条事实增加 `source_chapter`、`valid_from`、`valid_to`、`supersedes`、`confidence`。
- 检索分数融合：硬事实优先级、章节新近度、关键词、实体、语义相似度。
- 写章前生成“最小上下文包”，只带与本章人物、地点、比赛和伏笔有关的记忆。
- 新增记忆召回评测：该出现的事实是否出现、过期事实是否被错误召回。

### P1-2 候选稿采用有限竞争

- 普通章节默认 1 稿 + 定向修订。
- 黄金三章、卷末、关键转折可生成 2 个候选。
- 先过硬规则，再由商业裁判择优。
- 严格限制模型调用次数，避免多智能体无限讨论。

### P1-3 拆分 `gui_app.py`

当前 `gui_app.py` 约 11,599 行。建议依次拆出：

- `book_runner.py`
- `model_router.py`
- `usage_ledger.py`
- `gate_service.py`
- `project_service.py`
- `gui/` 下仅保留界面与事件绑定

每次只拆一个责任并保持测试全绿，避免大爆炸式重构。

## 五、P2：整书流程稳定后再做

- 番茄真实数据回流，只允许调整未发布章节。
- 提示词 A/B 和模型成本/质量看板。
- 图谱检索；只有人物和组织关系达到普通台账难以维护时再引入。
- 多智能体协作；只有固定评测证明优于单流程时再启用。

## 六、足球项目策略修正状态

2026-08-17 已完成从“全部原创”到分层策略的修正，当前项目合同为：

- 真实联赛、杯赛、国家队体系、转会窗和可核验公开制度可以直接使用。
- 真实俱乐部可作为现实坐标使用，但不虚构其违法、黑幕、私生活或未公开内部事实。
- 真人仅用于可核验的公开事实、名单、比赛结果和既有职业经历，不替真人编造私生活、争议、伤病、合同或反派行为。
- 长期队友、教练、经纪人、核心对手和承担主要戏剧冲突的人物使用原创角色。
- 不用绰号、谐音和影射规避；要么公开事实直述，要么完全原创。

该策略已经写入项目配置、人物边界和当前状态。真实人物/俱乐部事实截止日为2026-08-17；写到对应阶段前仍需刷新官方资料。正文尚未开始，因此下一步不是继续改设定，而是经明确授权后做首章真实生产验收。

## 七、验收标准

P0 完成的定义：

1. 不启动 GUI 也能从第 1 章生成到指定批次终点。
2. 任意状态强制中断后重启，不重写已正式提交章节，不丢状态，不产生重复回执。
3. 第 15 章生成完整交接包并停止；新会话可从第 16 章继续。
4. 第 30 章不会被误判为完结，能自动扩展 31—60 章规划窗口。
5. 每章均有正文、审查、状态更新、时间记忆和提交哈希的完整证据链。
6. 只有完结合同通过才能标记全书完成。
7. 模型和提示词变更必须通过固定评测集，且关键指标不低于基线。
8. 全量自动化测试通过，并新增整书状态机、15 章交接、30 章扩窗、崩溃恢复和模型路由测试。
